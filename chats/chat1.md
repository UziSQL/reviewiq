# ReviewIQ café review analysis

_Started 2026-11-15 08:25 UTC_

---

## User

Design a bilingual (English / Kazakh) web app called ReviewIQ. It is a working MVP for a university startup project, so every screen must be real, usable UI, not a landing page.  ## Product context ReviewIQ helps owners of small independent cafés and restaurants in Kazakhstan (Astana, Almaty) turn a batch of customer reviews from 2GIS and Google Maps into a short list of recurring problems. Each problem shows the original reviews that support it, and the owner picks one concrete operational check to do next. User: a café owner or shift manager, 30–50 years old, busy, not technical, often on a laptop between shifts or on a phone. They distrust "magic AI" and want to see evidence. They read Russian and Kazakh; the interface must work fully in English and Kazakh. Tone: calm, competent, practical, like a well-made printed report from an experienced restaurant consultant. Not a tech startup and not a marketing site.  ## Core journey (all screens and states are required) 1. Entry    - Header: wordmark "ReviewIQ", language switch EN | ҚАЗ (a segmented control, clearly visible, current language marked).    - Short headline: "What should your café investigate first?" plus a one-line explanation.    - Venue name field.    - Large textarea: "Paste reviews, one per line" (Russian, Kazakh or mixed). Helper text: 3–200 unique reviews, up to 4,000 characters each.    - Required checkbox: "I have permission to use these reviews and removed personal details."    - Primary button "Find recurring topics"; secondary "Load demo reviews".    - Side panel "How it works" with 3 steps, plus an honest limits note: "This prototype uses a keyword dictionary, not an AI model. Nothing is sent to a server." Pilot offer: "7-day trial, then optional 7,000 KZT / month." 2. Results    - Title "[Venue] — review priorities".    - Summary row with three numbers: unique reviews · recurring topics · reviews without a match. Note line: "2 exact duplicates removed."    - A ranked list of up to 3 topics (e.g. Waiting time 3/12, Staff interaction 3/12, Food temperature 2/12). Each item: rank number, topic name, count as "3 of 12 reviews" with a thin proportional bar, a suggested check in one sentence, and a "Show source reviews" action. 3. Evidence panel (opens for the selected topic)    - The original reviews with stable IDs (R01, R04, R07) in monospace, the matched keyword highlighted inside the text, and the review language tag (RU / KZ / Mixed). 4. Action    - The suggested check, plus fields "Person responsible" and "Review date", button "Save action". Saved confirmation state. 5. Feedback    - "How useful was this for choosing what to investigate?" as a 1–5 scale (5 clearly labelled buttons, not a dropdown), a comment field, "Save feedback" and "Export session (JSON)".    - Footer actions: "Edit input", "Reset session".  ## Required non-ideal states (design each one) - Error: permission not ticked; fewer than 3 or more than 200 reviews; empty venue name. Inline, next to the field, in plain language, never only red color. - Empty state: no recurring topic found → "No topic repeats in at least two reviews. This does not mean there are no problems — read the reviews manually." Show the unmatched count. - Save without selecting a topic or date → inline hint. - Success confirmations for saved action, saved feedback and export.  ## Bilingual requirements - Every label, button, helper text, error and empty state exists in EN and KZ. Show the layout in both languages. - Kazakh strings are often 20–40% longer: buttons and labels must wrap or grow, never truncate. - Fonts MUST render Kazakh Cyrillic correctly: test with "Әә Ғғ Ққ Ңң Өө Ұұ Үү Һһ Іі". Use e.g. IBM Plex Sans + IBM Plex Mono, or PT Sans/PT Serif, or another family with full Kazakh coverage. - Mark Kazakh text as a draft for human review; do not invent claims in either language.  ## Visual direction: "operations notebook / editorial ledger" - Warm paper background (around #F5F2EA), near-black ink text (#1D1C1A), one restrained accent: deep green (#1F5C4A) for primary actions and highlights. One muted warm secondary (ochre, around #B9822F) used only for keyword highlights. No other colors. - Structure with typography, spacing and 1px hairline rules, not with shadows and boxes. Corner radius 2–4px max. No floating cards with drop shadows. - Strong typographic hierarchy: a serif or confident grotesk for headings, a quiet sans for body, monospace for review IDs and counts. Tabular figures for all numbers. Big, confident numbers in the summary row. - Ranked topics read like a ledger or table of contents: large rank numerals (01, 02, 03), left-aligned, thin divider lines, a proportional bar drawn as a simple line. - Source reviews look like index cards or receipts: off-white slip, monospace ID in the corner, matched phrase underlined or highlighted with ochre. - Left-aligned asymmetric layout on a 12-column grid with generous margins; content max width ~1100px. Do not center the hero. - Icons: none, or very few thin line icons. Plain text labels are preferred. - Motion: minimal, functional only (panel open, saved confirmation). Respect prefers-reduced-motion.  ## Strictly avoid (these make it look AI-generated) Purple/blue/pink gradients, gradient text, glassmorphism, glow effects, dark neon themes, sparkle ✨ or magic-wand icons, robot/brain illustrations, emoji, "AI-powered" badges, three identical feature cards with icons, centered hero with a big gradient blob, heavy shadows, pill-shaped everything, stock photos, fake logos/testimonials/statistics, buzzwords ("unlock insights", "supercharge", "revolutionize"), Inter as the default font.  ## Accessibility and responsiveness - WCAG AA contrast (4.5:1 for text), visible focus outline, real labels on every field, 44px minimum tap targets, errors announced (aria-live) and never conveyed by color alone. - Show desktop (1440px) and mobile (375px). On mobile the evidence panel becomes a full-width section below the selected topic.  ## Deliverable If you produce code: one self-contained HTML file (HTML + CSS + vanilla JS, no frameworks, no external requests except optional web fonts), all UI strings in a translation object { en: {...}, kk: {...} } bound via data-i18n attributes, <html lang> switching between "en" and "kk", and every state above reachable by actually using the app with the demo reviews.
